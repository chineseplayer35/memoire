# 架构：四层记忆

```
用户消息
   │
   ▼
[当下上下文]  最近 50 条（4h 无对话先提炼再裁）
   │
   ├─ 最近 15 条里出现的人 ──→ [印象卡]（≤240 字/人，常驻注入）
   │
   ├─ 本会话最近 7 天 ───────→ [会话事记]（最近 7 条常驻）
   │
   └─ 重要的约定/情绪 ───────→ [日记]（最近 10 条常驻）
   │
   ▼
工具按需召回（仅当模型需要时）
   ├─ memory_read_impression  被提及但不在场的人
   ├─ memory_read_entries     按日期翻旧事记
   ├─ memory_read_diary       翻更早的日记
   ├─ memory_update_impression 主动更新印象卡
   └─ memory_write_diary      主动记重要的事
   │
   ▼
后台定时任务（每天几次，无互动不触发）
   ├─ 每日 22:30：事记压缩修订 + 印象卡梳理
   └─ 4h 空闲前：先提炼再裁剪上下文
```

## 数据流（每天）

1. 聊天只写入消息历史（DB），**不触发任何记忆模型调用**。
2. 每次 LLM 请求时，按规则注入：在场人印象卡 + 最近 7 条事记 + 最近 10 条日记（临时片段，不进历史）。
3. 需要时模型自己调工具取更多记忆（印象/旧事/旧日记）。
4. 每天 22:30，对有新消息的会话/人做一次提炼（事记 + 印象卡），写入文件。
5. 4 小时无对话时，先提炼该会话，再把上下文裁到 50 条。

## 文件布局

```
data/memory/
  people/<qq号>.md        # 印象卡（每人一份）
  people_index.json       # qq号 → 昵称/别名
  sessions/<安全umo>/YYYY-MM-DD.md  # 每会话每天一条事记
  diary.md                # 日记（重要的事，每行一条）
  state.json              # 游标/参与人/上次提炼时间
  usage.jsonl             # 每次后台调用的用量
```

## 为什么这样就不会"记忆稀碎"

- **不靠检索**：人在场才给卡，避免把无关旧记忆塞进回复。
- **不靠命中**：印象卡持续更新，重要性不靠"被提到几次"维持。
- **不靠全量**：提炼只处理增量，旧事按日期翻，成本不随时间膨胀。
